### R3-01
- Severity: blocker. Category: correctness.
- Branch/file:line: DASH `index.html:1345` (answer handler); ROUTES `routes.js:38` (PATCH route), `routes.js:61` (`transitionRequest`).

### R3-07
- Severity: major. Category: plan-gap.

### R3-08
- Severity: major. Category: correctness.
- Branch/file:line: DASH `index.html:1318` (`more = batch.hasMore === true`), `index.html:1307-1319` (cursor); ROUTES `routes.js:30-33` (events response).
- Plan item: persistence / 6 (point 3).
- Defect, part A (narrow): `load()` sets `window.registryRevision` (`index.html:1268`). The forms send `Number(window.registryRevision || 0)` (`index.html:1343-1344`). Revision 0 goes out only when a form is submitted before the first load completes, or after a failed load. The server then returns 409 (`routes.js` `stale()`), and the UI shows "Registry changed. Refresh and try again." (`index.html:1338`). The answer form sends no snapshot revision at all (`index.html:1345`).
- Defect, part B: The events route returns `{items, nextCursor}` with no `hasMore` and at most 100 items (`routes.js:31-33`). The UI loop expects `hasMore` (`index.html:1318`). It reads one batch per 5 s tick, so a backlog above 100 events replays slowly. The stored `registryCursor` (`index.html:1307, 1315`) is never compared with the server. If the store resets, the stored cursor is above all server cursors, and new events are never seen.
- Evidence: `routes.js:33` has no `hasMore` key. `grep -n hasMore` on DASH `index.html` shows lines 1269 and 1318 only.
- Fix: `routes.js` (add `hasMore`); `index.html` (loop until a batch has fewer than 100 items; reset a cursor that is above the server value).

### R3-11
- Severity: major. Category: correctness.
- Branch/file:line: DASH `REGISTRY-VIDEOS.md` lines 57, 59, 65, 67, 75-78.
- Plan item: verification.
- Defect: Wrong or unusable steps:
  1. Lines 57 and 59 end with `\\` (two backslashes). In a shell this is a literal backslash, so the curl command splits and fails.
  2. Lines 56-60 and 63-65 use line names. The forms need line IDs (R3-07). The guide does not say to read `id` from the `POST /api/lines` response.
  3. Line 65 says "Save the returned request ID and revision". The UI never shows the request ID or revision in a row (R3-03). Case 5 cannot be done from the UI.
  4. Case 3 (lines 67, 75) needs an archive row. `POST /api/registry/refresh` exists (`routes.js:39`) and is wired (ROUTES `server.js:1327`). But the UI has no control for it, and the guide does not tell the validator how to call it. "Normal line workflow" is not defined. Case 3 has no tested path to a non-empty archive.
  5. Case 4 (line 76) fails because of R3-02. Case 5 (line 77) fails because of R3-01.
  6. Case 6 (line 78) says "Disconnect and reconnect" without a method (for example `context.setOffline(true/false)`). The page refreshes only when new events arrived while offline (`index.html:1320-1321`), and the guide has no step to create an event. The `online` handler checks at once (`index.html` online listener), so a long wait is not needed. Poll interval is 5 s (`index.html:1301`).
- Selector check: these selectors are correct. `#registryToggle` (169), `#registry` (173), `#registryQuery` (175), `#registryFilter` (176), `#registryRefresh` (177), `#registryContent` (178), `form#claimForm` (179), `form#requestForm` (180), `form#answerForm` (181), inputs `lineId, claim, targetLineId, text, requestId, revision`, one `button` per form, `.registry-row` (class set in `load`). No wrong selector found. `#registryStatus` is not used by the guide.
- Fix: `REGISTRY-VIDEOS.md`. Use single `\`. Use line IDs. Add steps for the request ID, the refresh call, the offline method, and a way to create an event.

## Spec item 6 text
Copied from the plan file, line 18, item 6:

> 6. Add a **global Registry dashboard** in the existing router UI, independent of the selected line. It must let a person inspect the **full retained current state** across all lines, not just search matches: all active/available/stale claims, all open/answered requests, recent merged/superseded archive entries, and recent events. Show counts by status, owner line, repository, contract/branch/commit reference, revision, last update/check time, and merge verification evidence; provide expandable item details. Include search, line/repo/status filters, explicit archive toggle, and pagination with next-page controls so a bounded API never silently hides items. Show the snapshot revision and refresh/reconnect state; reconcile live events against the current snapshot so updates from other lines appear without a page reload. Keep the dashboard read-only; in a selected line's **Work / Requests** view, let the line publish claims and submit or answer requests under the existing line ownership rules. Display empty, stale, deleted-owner, and unverified states. Render all user-supplied text as text, not HTML. Do not expose raw transcripts, credentials, or unretained history. No automatic cross-line code merge or planner context injection beyond compact notification and an explicit discovery instruction.
