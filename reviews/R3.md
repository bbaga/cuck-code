# R3 review: Registry dashboard UI

Reviewed: origin/bd9a6f54/registry-dashboard 20080036 (base 284ddf3), registry-routes af92604a, request-rules 41bf963d, merge-ledger 7a07cf34.
Paths below are in the dashboard branch unless stated. Line numbers: `router-prototype/web/index.html` at 20080036.

## Findings (most severe first)

### R3-01
- Severity: blocker. Category: correctness.
- Branch/file: registry-dashboard, web/index.html (answerForm handler, last script block); routes in registry-routes `handleRegistryRoute`.
- Plan item: 6 (and 3).
- Defect: The answer form calls `POST /api/registry/lines/:id/requests/:rid/answer`. That route does not exist. The real route is `PATCH /api/registry/lines/:id/requests/:rid`. It needs `state` (accepted/declined/fulfilled), `expectedRevision` and `expectedSnapshotRevision`. The UI sends `text` and `expectedRequestRevision` only.
- Evidence: registry-routes has only POST/PATCH for `claims` and `requests` plus `refresh`. Any other path returns 404 "Registry route not found". `transitionRequest` (request-rules) reads `input.expectedRevision` and `input.state`.
- Fix: web/index.html. Use PATCH, send `{state, expectedRevision, expectedSnapshotRevision}`. Add a state selector to the form. Update the test that asserts `expectedRequestRevision`.

### R3-02
- Severity: blocker. Category: correctness.
- Branch/file: web/index.html, claimForm and requestForm handlers.
- Plan item: 6.
- Defect: The claim form sends `claim` as a string. The server needs an object with `repo`, `branch`, `commit` (non-empty strings), and optional `title/summary/tags/status`. `validClaim` rejects any other shape, so every publish returns 400. The claim form has no repo/branch/commit fields.
- Evidence: `validClaim("text")` is false, so `claim()` throws TypeError "Invalid claim fields" (HTTP 400). Also the claim status set is `active/blocked/merged/released/abandoned`. The plan lists `planned/active/available/superseded/stale/merged`. That mismatch is in registry-routes, not the UI.
- Fix: web/index.html. Add the fields repo, branch, commit, title, summary, tags to claimForm. Send `{claim:{...}, expectedSnapshotRevision}`.

### R3-03
- Severity: blocker. Category: correctness.
- Branch/file: web/index.html, `load()` row builder.
- Plan item: 6.
- Defect: The row builder reads field names that the API does not return. Claims have `ownerLineId`, `title`, `summary`, `tags`, `updatedAt`. Requests have `state`, not `status`. Archive entries have `mergeEvidence` as an object, and `mergedAt`. The UI reads `sourceLineId||lineId`, `status`, `age`, `item.text||item.claim`, `mergeReference||mergeEvidence`, `item.snapshotRevision`.
- Evidence: For a claim, owner line, title, summary and update time do not show. For a request, `state` does not show. For an archive entry, `mergeEvidence` prints as "[object Object]". The status line prints "Snapshot revision ." because items have no `snapshotRevision`. The page response field `snapshotRevision` is stored only in `window.registryRevision`.
- Fix: web/index.html. Map real fields. Format evidence as text (repo, targetBranch, commit/PR, check time). Show the page-level `snapshotRevision`.

### R3-07
- Severity: major. Category: plan-gap.
- Branch/file: web/index.html, forms.
- Plan item: 6.
- Defect: The plan asks for a per-line Work/Requests view. The forms are global, in the dashboard section, and take a free-text line ID. The dashboard is therefore not read-only and has no per-line ownership context. The line ID is the router line UUID (`lines.has(lineId)`). REGISTRY-VIDEOS.md tells the user to enter the name `registry-source`, so the server returns 404 "Line not found".
- Evidence: `claim()` and `requestChange()` call `lines.has(lineId)` first.
- Fix: web/index.html. Move forms to a tab in each line card using the card's own line ID. Remove them from the global view.

### R3-08
- Severity: major. Category: correctness.
- Branch/file: web/index.html, `submit()` and `checkRegistryEvents()`.
- Plan item: persistence / 6.
- Defect, part A: `expectedSnapshotRevision` comes from `window.registryRevision || 0`. If the registry was never loaded, it sends 0 and gets 409. The 409 message does not trigger a reload. Also a 409 from a stale item revision is shown as a generic message.
- Defect, part B: Events replay is weak. The server returns `{items, nextCursor}` with at most 100 items and no `hasMore`. The UI loop reads `hasMore` (always undefined), so it fetches one batch per 5 s tick. The cursor is stored in `localStorage` and is never compared with the snapshot. If the router storage is reset, the stored cursor is larger than any server cursor and new events are never seen.
- Evidence: routes.js `events` branch returns no `hasMore`; UI line `more = batch.hasMore === true`.
- Fix: registry-routes (add `hasMore`) and web/index.html (loop until `items.length<100`; reset cursor if `nextCursor` is below the stored value; no poll for refresh state UI).

### R3-09
- Severity: major. Category: correctness.
- Branch/file: web/index.html, `load()` and `checkRegistryEvents()`.
- Plan item: 6 (point 3).
- Defect: The refresh and reconnect state is not shown. Poll errors overwrite the single status line. Offline, paused (hidden tab) and "Will retry" states have no indicator. The poll runs only while `!document.hidden && navigator.onLine`, with no visible "offline" label. Events refresh only if the dashboard is open and visible.
- Evidence: `catch (err) { status.textContent = String(err) + ". Will retry." }`.
- Fix: web/index.html. Add a state label (live / offline / reconnecting / replayed N events).

### R3-11
- Severity: major. Category: correctness.
- Branch/file: REGISTRY-VIDEOS.md.
- Plan item: verification.
- Defect: The guide has these wrong or unusable steps:
  1. The curl examples end lines with `\\` (double backslash). The shell sees a literal backslash, and the command breaks.
  2. Lines are created with names, but the forms need the line ID. The response `id` must be used.
  3. Case 5 says "save the returned request ID and revision". The UI never displays request ID. The row has no `id`. The case cannot be done from the UI.
  4. Case 3 needs a merged archive entry "through the normal workflow". Merge verification needs `POST /api/registry/refresh` with evidence, which has no UI and no server wiring (R3-04).
  5. Case 4 cannot pass because of R3-02. Case 5 cannot pass because of R3-01.
  6. Selector `form#claimForm button` etc. is correct: the markup has `id="claimForm"` and one `button` per form. IDs `#registryToggle`, `#registry`, `#registryQuery`, `#registryFilter`, `#registryRefresh`, `#registryContent` exist.
  7. Case 6: polling is every 5 s, so the replay step needs a wait. The guide gives none.
- Evidence: `grep -n '\\\\\\\\' REGISTRY-VIDEOS.md` shows the double backslashes in the two curl examples.
- Fix: REGISTRY-VIDEOS.md. Use single `\`, use line IDs from the API response, show request ID in the UI, add a wait step.
